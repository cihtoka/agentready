# 선택 지표 가이드라인 (추론 기반)

이 문서의 항목은 AI 쇼핑 에이전트의 동작 방식과 업계 자료에서 추론한 권고이며, 에이전트별 실제 선택 기준은 공개되어 있지 않다.

## ssr.why: 정적 HTML 상품 정보가 필요한 이유
에이전트가 상품 페이지에서 상품명과 가격을 읽으려면 그 값이 HTML에 이미 들어 있는 편이 안전하다. 브라우저를 쓰는 에이전트는 자바스크립트를 실행할 수 있지만, 크롤러나 검색엔진이 만든 자료원은 렌더링하지 않는 경우가 많다. 본문이 비어 있고 스크립트로만 채워지는 페이지는 읽기 비용이 커서 후보에서 밀릴 수 있다(추론 기반 권고).

## ssr.fix: 정적 HTML 상품 정보를 서버에서 렌더링하는 방법
상품명(h1), 가격, 재고, 핵심 설명을 서버가 만든 HTML에 직접 넣고, 화면을 꾸미는 부분만 자바스크립트로 처리한다. 빈 root 요소에 스크립트가 채우는 구조라면 서버 렌더링이나 사전 렌더링을 도입한다. 이 항목은 개발 구조 변경이 필요해 자동 수정 도구가 없다.

## ssr.example: 정적 HTML 상품 정보 서버 렌더링 예시
나쁜 예는 <div id="root"></div> 와 스크립트만 있는 페이지다. 좋은 예는 <h1>원목 사이드 테이블</h1><p>89,000원</p><p>국산 오크 원목…</p> 가 응답 HTML에 처음부터 포함된 페이지다.

## policy.why: 배송·반품 정보가 필요한 이유
에이전트는 같은 상품을 파는 여러 판매자를 비교할 때 가격뿐 아니라 배송 속도·비용과 반품 조건을 함께 비교한다. 배송·반품 정보가 없으면 비교표의 칸이 비어 감점되거나 후보에서 제외될 수 있다(추론 기반 권고).

## policy.fix: 배송·반품 정보를 노출하는 방법
상품 페이지 본문에 배송비, 도착 예정일, 반품·교환 가능 기간과 조건을 문장으로 적고, JSON-LD 에는 offers.shippingDetails 와 hasMerchantReturnPolicy 로 구조화한다. 값은 반드시 실제 정책과 같아야 하므로 운영팀이 직접 입력한다. 이 항목은 자동 수정 도구가 없다.

## policy.example: 배송·반품 정보 예시
나쁜 예는 배송 안내가 별도 탭이나 이미지 안에만 있는 경우다. 좋은 예는 본문에 배송비 3,000원, 평일 14시 이전 주문 시 당일 출고, 7일 이내 무료 반품·교환을 적고 JSON-LD 의 shippingDetails, merchantReturnDays 와 맞추는 것이다.

## reviews.why: 리뷰와 평점이 필요한 이유
리뷰 수와 평점은 에이전트가 후보를 거를 때 쓰는 신뢰 신호로 알려져 있다. 평점이 구조화되어 있지 않으면 에이전트가 본문에서 숫자를 추측해야 하고, 리뷰가 없는 상품은 비교에서 불리할 수 있다(추론 기반 권고).

## reviews.fix: 리뷰와 평점을 노출하는 방법
JSON-LD Product 에 aggregateRating(ratingValue, reviewCount)을 넣고 화면에도 같은 값을 보여 준다. 리뷰는 실제 구매자의 후기에서 계산한 값만 사용해야 하며 임의로 만들어 넣으면 안 된다. 이 항목은 자동 수정 도구가 없다.

## reviews.example: 평점 구조화 예시
나쁜 예는 별 이미지만 있고 숫자가 없는 경우다. 좋은 예는 화면에 별점 4.8 · 리뷰 132개를 적고 "aggregateRating": {"ratingValue": "4.8", "reviewCount": "132"} 를 JSON-LD 에 넣는 것이다.

## consistency.why: 화면 가격과 구조화 가격이 같아야 하는 이유
에이전트는 JSON-LD, 피드, 화면 텍스트를 함께 읽는다. 값이 서로 다르면 어느 쪽이 맞는지 알 수 없어 신뢰도가 떨어지고, 결제 단계에서 가격이 달라져 구매가 중단될 수 있다(추론 기반 권고).

## consistency.fix: 가격을 일치시키는 방법
상품 데이터에서 화면 가격과 JSON-LD 가격을 같은 값으로 생성하도록 템플릿을 통일한다. 값이 다를 때는 실제 판매 가격이 어느 쪽인지 먼저 확인하고, 틀린 쪽을 고친다. 자동 수정 도구는 JSON-LD 를 화면 가격에 맞추지만 어느 쪽이 맞는지는 사람이 확인해야 한다.

## consistency.example: 가격 불일치 예시
나쁜 예는 화면에 24,900원인데 JSON-LD 의 offers.price 는 29900 인 경우다. 좋은 예는 화면의 24,900원과 JSON-LD 의 "price": "24900" 이 같은 값에서 만들어지는 경우다.

## overlays.why: 팝업과 배너가 방해되는 이유
브라우저로 움직이는 에이전트는 화면을 가리는 팝업, 쿠키 배너, 모달 때문에 클릭이 막히거나 단계가 늘어난다. 닫기 버튼을 찾지 못하면 작업을 포기하고 다른 후보로 넘어갈 수 있다(추론 기반 권고).

## overlays.fix: 팝업과 배너를 줄이는 방법
첫 방문 시 전체 화면을 가리는 이벤트 팝업은 없애거나 페이지 본문 안의 배너로 바꾼다. 쿠키 안내는 화면을 가리지 않는 하단 띠로 두고, 닫기와 동의는 표준 button 으로 만들며 role="dialog" 와 접근 가능한 이름을 붙인다. 이 항목은 디자인과 정책 결정이 필요해 자동 수정 도구가 없다.

## overlays.example: 팝업 예시
나쁜 예는 position:fixed 로 화면 중앙을 덮고 닫기 요소가 div 의 onclick 뿐인 이벤트 팝업이다. 좋은 예는 본문 상단에 배너를 두고 닫기를 <button aria-label="닫기"> 로 제공하는 방식이다.

## friction.why: 로그인과 캡차가 구매 장벽인 이유
로그인이나 회원가입이 필요하면 에이전트는 사용자에게 제어권을 넘겨야 하고, 캡차는 자동화된 접근을 막는다. 구매 단계의 장벽이 많을수록 에이전트가 구매를 끝까지 진행하기 어려워진다(추론 기반 권고).

## friction.fix: 구매 장벽을 줄이는 방법
비회원 구매 경로를 제공하고, 장바구니와 주문 단계에는 캡차를 두지 않는다. 로그인이 필요한 경우에도 상품 조회, 가격 확인, 장바구니 담기는 로그인 없이 가능하게 한다. 봇 차단 설정은 이 점검의 대상이 아니라 보안팀이 별도로 확인한다. 이 항목은 자동 수정 도구가 없다.

## friction.example: 구매 장벽 예시
나쁜 예는 장바구니 페이지에 로그인 후 주문하실 수 있습니다 라는 문구만 있고 비회원 경로가 없는 경우다. 좋은 예는 비회원도 바로 주문할 수 있어요 라는 안내와 함께 이메일만으로 결제까지 진행되는 경우다.
